# Managing Git Safely

Preserve user intent and authorization boundaries. Tool availability does not grant permission to publish, merge, delete, force-update, or clean work.

Choose the smallest operating mode in [Workflow modes](references/workflow-modes.md) before acting. The seven stages are a reference map, not universally required steps. For an unqualified request to implement, fix, or change work, default to **Complete delivery** through verified Squash Merge into the actual default Branch. Use another endpoint when the user explicitly asks for explanation only, an Issue, local work, or Draft delivery. Resume an existing Branch or Pull Request at its current valid stage instead of recreating completed artifacts.

1. Explain a new concept with its English term first and Korean term beside or below it. Keep Pull, Pull Request, Commit, Push, Merge, and deployment distinct.
2. When a user asks to update “the README” without naming a language-specific exception, first identify every maintained language README variant and update all of them with semantic parity for commands, links, license facts, installation paths, examples, and safety rules. Before completing the update, compare commands, links, installation paths, license facts, examples, and safety rules across every maintained language variant. Record the per-category parity result in a PR body, verification checklist, or test output as reportable verification evidence.
3. Before drafting a README, Issue, or Pull Request, read [Writing guidelines](references/writing-guidelines.md). Before Issue or Pull Request work, read the target Repository's `CONTRIBUTING` and templates; use this package's [contribution guidelines](CONTRIBUTING.md) as the general fallback. Search existing Issues and Pull Requests before drafting new work. Use one independently reviewable outcome per Pull Request: keep implementation, tests, documentation, and configuration together when they solve the same root cause, and split work that can be reviewed, verified, merged, and reverted independently. Use the title grammar and English publication-first/Korean-review-copy order in [GitHub workflow](references/github-workflow.md). The Korean review copy must translate every required field and section completely. It must not use “same as above”, “위와 동일”, a summary, or a cross-reference to the English section.
4. Before an authenticated GitHub operation, distinguish installed, authenticated, authorized, and usable states. If GitHub CLI is selected, read [GitHub authentication](references/github-authentication.md), use browser-only interactive authentication, protect device codes and tokens, verify the exact account and scopes in the same execution environment, and resume the approved workflow automatically when login succeeds. Authentication does not authorize Push or Merge; those actions remain inside the delivery authorization contract.
5. For publication or Merge work, read [Delivery contract](references/delivery-contract.md). Use one Start authorization for the stated scope and one exact-state Final Merge authorization. Continue through already authorized stages without asking the user to say “next”; at every update, label the overall delivery state and list the current and remaining stages.
6. Before worktree, authorship, publication, review, merge, cleanup, or recovery work, read [collaboration policy](references/collaboration-policy.md). Before the first Push to a PUBLIC remote, review all reachable Git history intended for publication, including author/committer identity and email metadata. Use a GitHub-provided `noreply` email as the default-safe public Commit identity. General publication approval does not authorize a personal or unapproved non-noreply email; if one is reachable, stop and do not Push. Never direct Push to the repository's actual default Branch, whatever its name; `main` and `master` are examples. Never use Force Push or make unapproved public publication. Stop if ownership, scope, checks, secret handling, or the applicable authorization gate is unclear.
7. Never translate impact into an unknown priority code or scale. Use the confirmed repository taxonomy; otherwise state the observed impact, set `Priority` to `Needs confirmation`, and list the taxonomy under `Open Questions`.
8. For Merge, final authorization applies only to the displayed exact Pull Request, Base Branch, Head Branch, Head SHA, current checks, unresolved reviews, required reviews, mergeability, method, and expected Squash title. Any new commit, base/title/method change, failing check, conflict, or blocking review invalidates it and requires a new approval. A normal pending-to-passing check after Ready does not invalidate approval. Return to Draft before corrective or new-state development. After Ready for review, wait and re-check GitHub requirements. Use only Squash Merge through the Pull Request; pass the approved title with `--subject` and read [collaboration policy](references/collaboration-policy.md) for the detailed procedure.
9. For plain-language definitions and license explanations, read [Git and GitHub Concepts](references/github-concepts.md). For stage execution, read [GitHub workflow](references/github-workflow.md).

When facts are unknown, list them under `Open Questions`; do not guess.
