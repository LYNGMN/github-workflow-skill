# Collaboration Policy

This policy is tool-neutral. It applies whether work is performed with a terminal, desktop app, IDE, or AI assistant.

## Ownership and dirty worktrees

Use one author per Branch/Worktree. Before changing a dirty worktree, identify the owner, each changed file’s purpose, and whether the changes belong to this task. Do not stash, reset, discard, move, delete, or combine another author’s work merely to make status look clean.

## Reversible checkpoints and publication

Create a fresh, single-purpose Commit after inspecting staged and new files, checking sensitive data, and running relevant tests. An interrupted, unverified task may be preserved as a local WIP checkpoint. Confirm remote identity, visibility, branch, included files, and approval scope before Push. A first Push, new remote, or new delivery scope requires the Start authorization defined in [Delivery contract](delivery-contract.md); unapproved public publication is prohibited. Once that exact scope is approved, later non-force updates to the same work Branch and Draft Pull Request do not require repeated stage-by-stage approval. Before the first Push to a PUBLIC remote, review all reachable Git history intended for publication, including author/committer identity and email metadata. Use a GitHub-provided `noreply` email as the default-safe public Commit identity. General public approval does not authorize publishing a personal or unapproved non-noreply email. If one is reachable, stop and do not Push; an explicitly pre-approved organizational or public alias is the only exception. If the metadata was already published, keep publication stopped and report the affected Commit count and remediation choices without repeating the email address. Never direct Push to the repository's actual default Branch, whatever its name; `main` and `master` are examples. Never use any Force Push variant.

## Review and Merge

Keep Pull Requests as Drafts until final authorization. Before approval, show the exact Pull Request, Base Branch, Head Branch, Head SHA, current checks, unresolved reviews, required reviews, mergeability, method, and expected Squash title. One explicit final approval for that exact state authorizes the Ready for review transition and Squash Merge after all GitHub requirements pass. After Ready for review, re-check that Head, Base Branch, title, and method are unchanged; re-check reviews, checks, conflicts, mergeability, and that Squash Merge is enabled; and wait for required Code Owner reviews and checks without asking for another approval when a normal pending check passes. Any new commit, base/title/method change, failing check, conflict, or blocking review stops Merge, invalidates the existing final approval, and requires a new exact-state final approval after resolution. A new commit, base/title/method change, or any corrective development must return the Pull Request to Draft before retest and re-review. A transient failed check, conflict, or blocking review still stops Merge and invalidates approval; if correction resumes, the Pull Request must return to Draft before retest and re-review. If development resumes, convert back to Draft, retest, re-review, and obtain a new final approval. Only Squash Merge through the Pull Request is allowed; use `--match-head-commit` for the exact Head and `--subject` for the approved title, and never bypass protections with `--admin`. Do not rewrite or Force Push merely to combine branch commits. After Merge, verify the default-branch Squash SHA, Pull Request merged state, and linked Issue closure. Follow [Delivery contract](delivery-contract.md) for the two authorization gates and unambiguous progress labels.

## Recovery and cleanup boundaries

Deployment is separate from Merge. Branch deletion and worktree cleanup are also separate: they need exact targets, proof of recoverability, and separate approval. Do not use `git clean`, `git reset --hard`, `git checkout .`, `git restore .`, or an IDE’s discard-all action without those boundaries being met.
